# Vettr launch-readiness audit — 2026-09-28

**Scope:** Audit only. No application code changes. Local stack exercised with seeded fake data; production (`https://vettr.pages.dev`) and staging (`https://staging.vettr.pages.dev`) inspected read-only (no accounts created on prod).

**Versions observed:** web `5.0.254` (prod + local), API health `5.0.139`, extension `5.0.30`, staging web still `5.0.219`.

**Environment used:** Cloud VM — PostgreSQL 16 + local Express `:3001` + Vite `:5173`, 12 seeded `market_deals` rows, test users `beta-tester@example.com` / `audit-user-{a,b}@example.com`.

**Could not test (called out below):** Chrome extension UI in Chrome; live Google Gmail/Calendar OAuth; real SMTP delivery; Stripe Checkout with live/test keys; multi-member team share approval flows end-to-end; DD external portal as a non-owner; Web Push on a real device; Granola meeting notes (MCP auth unavailable in this environment).

Screenshots live in [`shots/`](./shots/).

---

## Executive snapshot

The product loop (buy box → matching feed → calculator → Quick IOI → save to CRM Cards) works locally and the public guest feed on prod loads **~41k** deals through the Worker→Mac API path. Isolation between personal saved deals looks solid in API checks. The main launch risks are **ops SPOF (API/DB on a Mac)**, **legal/OAuth packaging (blank `/terms`, thin privacy)**, **missing abuse controls (no rate limits, weak email validation)**, and **billing/SMTP not production-ready** while the landing page already sells Pro.

## (a) Launch blockers

Items that should be resolved (or explicitly accepted with a mitigation) before inviting strangers.

| # | Finding | Evidence | Suggested fix | Size |
|---|---------|----------|---------------|------|
| A1 | **Production API + Postgres run on Jamie’s Mac via Cloudflare tunnel** — single point of failure for all signed-in and guest deal traffic | `DEPLOY.md`, `CONFIG.md`; prod `GET /health` → `5.0.139` via `vettr-api.metzgerbuildsthings.workers.dev` | Document always-on Mac + UPS; add uptime check on `/health`; schedule `pg_dump` off-box; plan migrate API/DB to a small always-on host before paid launch | L |
| A2 | **No Terms of Service; `/terms` is a blank black screen** | No `terms` route in `web/src/App.jsx`; prod screenshot [`shots/prod-terms-spa.png`](./shots/prod-terms-spa.png); privacy exists only as static HTML | Add real Terms page (and route `/terms` + footer links). Required for Google OAuth verification / store listing | M |
| A3 | **Privacy policy is Chrome-extension-scoped** — does not cover web account, CRM, Gmail send, Calendar tokens, push, digests | `web/public/privacy-policy.html`; landing/login/register have no Privacy/Terms links | Rewrite privacy for full product; link from landing, register, settings, extension store listing | M |
| A4 | **Password reset depends on SMTP; without it users get a success message and no email** | `authController.forgotPassword` always returns generic success; logs reset URL only when `!mail.sent`; local `.env` has no SMTP | Confirm prod SMTP (or Resend) works; surface “email delivery unavailable” to admins; smoke-test forgot-password before beta invites | S |
| A5 | **No rate limiting on `/api/auth/*` (or anywhere)** | 10 failed logins all returned `401` with no throttle; no `express-rate-limit` / helmet in backend | Add IP rate limits on login/register/forgot-password; consider CAPTCHA if abuse appears | S |
| A6 | **Google scopes `gmail.send` + `calendar.events` need verification for broad users** | `googleCalendarService.js` `SCOPES`; unverified apps hit Google’s “unverified app” wall | Start Google OAuth verification now (needs A2/A3); or ship beta with “Open in Gmail” only until verified | L |
| A7 | **Chrome extension requests `<all_urls>` content scripts + `https://*/*` host permissions** | `manifest.json` | Narrow matches to listing domains you scrape; justify remaining permissions in store listing — otherwise Web Store / enterprise IT will block | M |

## Recommended beta sequence (1–2 weeks, thin slices)

1. **Day 1–2 — Trust & legal:** Ship Terms + updated Privacy; footer links; fix blank `/terms` (A2/A3/B2/C4).
2. **Day 2–3 — Abuse basics:** Rate-limit auth; validate email format; fail-closed scrape secret in prod (A5/B4/C8).
3. **Day 3–4 — Ops hygiene:** Health uptime monitor; first off-box DB backup + restore drill; document Mac wake/sleep policy (A1/E).
4. **Day 4–5 — Auth email path:** Prove forgot-password email in prod SMTP; beta admin feedback inbox (A4).
5. **Day 5–6 — Product polish that blocks confidence:** Archive badge (B1), tab badge spacing (B3), calculator 100% default (B5), Billing CTA when Stripe off (B10).
6. **Day 6–7 — Google path:** Either submit OAuth verification **or** message beta users to use “Open in Gmail” until verified (A6).
7. **Day 7–8 — Staging + CI:** Refresh staging; add test CI job; close stale PRs (B7/C3/C11).
8. **Day 8–10 — Invite 5–10 buyers:** Personal workspaces only; collect Feedback widget bugs; defer Stripe/Off-Market until loop is sticky.
9. **After first cohort:** Extension permission narrowing (A7) before Web Store push; Sentry (D2); Stripe Pro alerts (D3).
